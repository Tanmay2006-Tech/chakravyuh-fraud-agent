# How Chakravyuh meets the judging criteria

| # | What success looks like | Where it happens | Where to see it |
|---|---|---|---|
| 1 | Investigate from an initial trigger | `workflow.intake` handles risk-score, customer-report and analyst-request triggers identically | Console, any case: trigger text at the top |
| 2 | Gather evidence from the graph and other sources | 13 installed GSQL queries called through TigerGraph MCP (`agent/detectors.py`), plus the GDS graph algorithm `tg_wcc` (`agent/graph_algorithm.py`, weight-0 context); policy, pattern and regulatory passages via TigerVector GraphRAG; simulated customer and analyst responses (assumptions recorded in `evidence_requests`); the bank model's score as an external input | Evidence tab: every claim has `source`, `ref` (query or document) and entity IDs |
| 3 | Identify fraud patterns and assess risk | Detectors for card testing, threshold structuring, shared-origin rings, CNP bursts, region novelty, fingerprint history; log-odds probability; pattern + episode selection (`agent/assess.py`); two undocumented schemes described in the agent's own words; TigerGraph GDS `tg_wcc` connected components over the card-in-use × rare-device projection (ring context in each case, 85 multi-device rings in `monitoring/wcc_rings.json`) | HHG-006, HHG-014 (undocumented), HHG-019 / HHG-011 (rings) |
| 4 | Create and progress a case | `InvestigationCase` written to TigerGraph when it opens, updated when it closes; a timeline records every stage (opened → evidence → memory → assessed → recommendation → evidence requested → response → final → closed/escalated) | Console: "Case record"; Savanna: `INV-HHG-0xx` vertex, `timeline` attribute and edges |
| 5 | Recognise insufficient or uncertain evidence | R1 single-signal check, independent-evidence count, the stopping rule of section 6; HHG-002 ends honestly uncertain under R4 | Fraud-chance bar (before vs after), "Why it stopped" |
| 6 | Gather more evidence through controlled actions | Step-up authentication, customer validation and analyst information, issued only through the action gateway (`agent/gateway.py`) as `auto` actions | Case record: "Requested … through a policy-approved channel" |
| 7 | Recommend actions and update them as evidence arrives | `initial` and `final` next-best actions, `what_changed`, plus a contingency plan for every possible reply (deny / confirm / silence), with R8 escalation when a confirmation contradicts strong evidence | "How the decision was reached" (first recommendation → what was asked → final, and a "What changed" line naming the rule behind each new action) and "The plan for every possible answer" |
| 8 | Explain evidence, reasoning, uncertainty and decisions | Every action cites its rule; evidence cites its query; probability before/after; SAR narrative following FinCEN guidance; LLM text is ID-checked | Every case page; Regulator report tab |
| 9 | Operate within policies, permissions and approvals | Policy R1–R10 and section 3a in code (`agent/policy.py`); the gateway executes `auto` actions only and queues L1/L2 for a team lead or fraud manager | "What to do now": approval badges and Approve/Reject queue |
| 10 | Use prior cases and outcomes as memory | Closed cases on the same fingerprint, device and card; semantic search over closed-case narratives; detector weights calibrated on the closed history (`scripts/calibrate.py`, AUC 0.45 → 0.66 out of time); earlier Chakravyuh investigations retrieved from the graph (see `monitoring/MON-001.json` citing `INV-HHG-006`) | Evidence tab ("bank memory: …"), "How it works" page |
| 11 | Present it through a usable interface | Streamlit console: 20-case overview, investigation rings, plain-language verdict, actions and approvals, contingency plan, case record, evidence, trace, SAR, answer file | Live console: `<Streamlit URL>` (or `streamlit run ui/app.py`) |
